# ADR-0008: Unity runtime для Gate3D v0.2 prototype

## Status

Accepted for the limited `Gate3D v0.2` interactive prototype after the user explicitly asked to embody the 3D space and later confirmed Unity and Blender were installed on the authorized host.

This ADR does **not** select the final MUSCA engine, does not change frozen GATE-P01 v0.1, and does not authorize Blender Form composition before Function approval.

## Context

ADR-0007 used a browser/Three.js graybox to validate circulation cheaply before an engine dependency existed in the verified toolchain. That work established the room contract: 16×30×5.2 m shell, axial route, mirrored reagent stations, 4.5 m gate, explainable HUD, contextual scan/select interaction, and physical world response.

After ADR-0007 was implemented, the host state changed materially: Unity 6000.6.1f1 and Blender 5.2.0 LTS were verified as installed. Unity Personal licensing resolved successfully. A Unity project could be created after diagnosing a process-environment defect in UPM startup.

## Decision

Create `unity/MUSCA-Gate3D/` as the authoritative interactive runtime for the Gate3D v0.2 prototype.

- Unity version: `6000.6.1f1`.
- Render pipeline: Built-in, no URP/HDRP package added.
- Input: existing legacy Input Manager axes; no project-settings binding mutation.
- State authority: plain C# `GateDomain`; Unity presentation does not own hidden truth.
- Scene: generated by an Editor builder rather than hand-edited YAML.
- Windows Development build is the verified runtime target for this milestone.
## Relationship to ADR-0007

ADR-0007 remains historical truth and a reproducible Function reference. It is not retroactively rewritten as a mistake. Its browser runtime remains useful for cheap state/room validation and CI.

Unity supersedes the browser runtime only as the **authoritative playable 3D prototype surface** for Gate3D v0.2.

Blender 5.2 LTS is reserved for authored shell/prop Form work after explicit human Function approval. It is not required for the current graybox runtime.

## Alternatives

1. Keep Three.js as the only runtime. Rejected for the next milestone because Unity is now available and provides the intended game-development surface.
2. Jump directly to Blender Form composition. Rejected before Function approval because art would make layout changes more expensive and would violate the room-production gate.
3. Add URP/HDRP immediately. Rejected because the graybox does not need a render-pipeline migration and package/network reliability is not yet cleanly verified.
4. Install a Unity MCP provider immediately. Deferred: no provider is currently detected in the project/tool surface, and repository + batch Editor automation is sufficient for this milestone.

## Consequences / price

The repository temporarily carries Python, browser-3D, and Unity prototype surfaces. They serve different evidence roles and must not be conflated.

Unity introduces a large local generated state (`Library`, `Temp`, `Builds`) that remains ignored. Only source assets, project settings, manifests, scenes, tests, and concise evidence are tracked.

The current verified build is Development, Windows-only, keyboard/mouse, single-player, and graybox quality. It is not a release candidate or final art benchmark.
## Tests / QA

Required evidence for this ADR:

- Unity Editor import/compile exits 0 on `6000.6.1f1`;
- generated scene validator reports PASS with zero missing scripts;
- camera FOV/eye height and station coordinates match the room contract;
- Unity Test Framework EditMode suite passes `7/7`;
- Windows Development build reports `Succeeded`, zero build errors;
- standalone player creates production-camera screenshots and JSON QA receipts;
- spawn HUD explains WASD/mouse/Q/E;
- station view exposes contextual `Q` scan / `E` selection without hidden answer leakage;
- `openedworld` capture visibly shows the physical gate open to Sector B;
- Python/frozen pilot behavior and participant data remain untouched.

A recurring Unity `Curl error 35` appears during external certificate checks on shutdown. It did not block local import, compilation, tests, scene validation, or Windows build. It remains a package/network-management risk, not a hidden PASS.

## Diff scope

`unity/MUSCA-Gate3D/`, `prototype3d/`, ADR-0007/0008, room evidence, selected QA images, `.gitignore`, documentation, and CI checks. No raw participant receipts, no scientific-result promotion, no frozen GATE-P01 payload mutation.

## Rollback

Close/delete `feature/3d-gate-prototype` and remove ignored local Unity generated state/builds. The prior `feature/visual-interface` branch remains intact. The browser Function reference can still be run from `prototype3d/`.
